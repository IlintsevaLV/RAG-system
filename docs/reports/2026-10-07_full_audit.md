## Резюме

Корпус RAG-system вырос с 24 A/B страниц до 9176 (26 документов). Retrieval работает:
- **lexical (BM25):** v1 0.92, para 0.23, paraphrase 0.00
- **dense (e5-small, min-dense 0.85):** v1 0.62, para 0.69, paraphrase 0.20
- **dense (e5-base, min-dense 0.85):** v1 0.46, para 0.77, paraphrase 0.20
- **hybrid (adaptive):** v1 0.69, para 0.31, paraphrase 0.20-0.30
- **negative examples:** «не найдено» при min-dense 0.85

**Пять узких мест:** (1) text_layer не валидируется, (2) единый чанкинг для разных типов, (3) e5-small слабая, (4) структура документа теряется, (5) нет честной оценки.

**Главный вывод:** проблема не в retrieval, а в **качестве данных** — text_layer и чанкинге.

<a name="чанкинг"></a>
## Чанкинг — почему получается мусор

### Как работает сейчас

**Пайплайн `retrieval build`:**

1. Читает `data/ir/pages/*_pages.json`
2. Фильтрует: класс A/B, status=ok, без low_confidence, без оглавления
3. Отсеивает мусор (`is_index_garbage`)
4. Режет текст на чанки по номерам пунктов (`27.1435.`, `2.5.2`, `Глава 4`)
5. Склеивает подпункты `(a)`, `а)` внутри родительского
6. Склеивает продолжение на следующей странице
7. Разбивает длинные (>1800 знаков) на фрагменты
8. Считает эмбеддинги

### Почему чанки плохие

#### Проблема A. Источник данных — разный

| Тип PDF | Пример | Что извлекается |
|---|---|---|
| Сканы (C/D) | `_1954`, `КТ-160G`, `ФАП 273` | OCR-мусор → отсеивается |
| S1000D XML | АС 1.1.S1000DR_2014 | XML-теги в тексте |
| Таблицы чисел | US_Army | `2.91:1 1.22:1 3,020` |
| FMEA-таблицы | RCM 21.1 | `31.13 to both pilots...` |
| Формулы как текст | РДК 89 | `L = 0.004[a ln 2a/ρ + ...]` |
| Хороший A/B | НЛГ-27, РЦ AC | `27.1435. Гидравлические системы (а)...` |

Пайплайн **один** для всех — не различает типы.

#### Проблема B. text_layer — не всегда «чистый»

- **Класс A** ≠ чистый текст
- **S1000D** (АС): text layer содержит XML
- **DOCX → PDF** (APR4754A): греческие двойники
- **Газетная вёрстка** (РЦ AC): порядок span-ов перепутан

`text_layer` **не валидируется** — берём как есть.

#### Проблема C. Чанкинг ломается на плохих данных

Пример (АС, S1000D) — 3 чанка из одного текста:
Chunk 1: "Глава 3.9.5.2.1.2 BRDP-S1-00106 Заполнение Решение..."
Chunk 2: "refs Разд. 2.6 <refs> η порядке заполнения. Если он элемента < >"
Chunk 3: "заполняется, необходимо задать порядок элементов в перечне."

Регексп `^Глава \d+\.\d+` разбил XML на 3 чанка.

#### Проблема D. Короткие чанки — 13%

- **3753 чанка < 50 символов**
- FMEA-строки (`31.13 to both pilots`) — полезны, но короткие
- Заголовки пунктов (`25.611 Accessibility provisions`) — полезны, но не самодостаточны
- Обрывки (`2. Provide 5. Provide`) — мусор

BM25 любит короткие — они вытесняют длинные.

#### Проблема E. Формулы как текст — 553 чанка

Формулы индексируются наравне с текстом. Должны быть в отдельном контуре (regions/).

### Итог по чанкингу

**Чанкинг не «плохой» — он «одинаковый для всех документов».**

Реальные проблемы:
1. Нет классификации типов контента (текст/таблица/XML/формула/FMEA)
2. Нет валидации text_layer
3. Чанкинг по номерам — работает на НЛГ-27, ломается на АС
4. Короткие чанки не отсеиваются
5. Формулы попадают в текстовый индекс

<a name="эмбеддинги"></a>
## Эмбеддинги — как строим, как проверяем

### Как строим

**Модели:** `intfloat/multilingual-e5-small` (384 dim), `intfloat/multilingual-e5-base` (768 dim).

**Пайплайн `build --dense`:**

1. Читает `chunks.jsonl`
2. Загружает модель
3. Для каждого чанка: префикс `passage: `, токенизация, forward pass, усреднение, L2-нормализация
4. Кэш по `sha256(text)` — не считает дважды
5. Сохраняет `dense.npy` (float32) + `dense_ids.json`

**Время:** e5-small ~1 час, e5-base ~2-3 часа (29028 чанков, CPU).

### Как проверяем

**Что проверяем:**
- Размерность `dense.npy`
- Соответствие `dense_ids.json`
- Модель в `meta.json`
- `--force` пересчитывает при смене модели
- Кэш по sha256

**Что НЕ проверяем:**
- Качество эмбеддингов (различение семантики)
- Согласованность префиксов
- Распределение cosine similarity
- Baseline для сравнения

### Метрики

| Метрика | Что измеряет | Наш результат |
|---|---|---|
| recall@1/3/5 | Попадание правильного чанка в top-k | 0.46-0.92 |
| MRR | Mean Reciprocal Rank | 0.47-0.77 |
| probe | Self-test (точная фраза) | 0.98 (lexical) |
| eval | Golden set (3 датасета) | v1/para/paraphrase |

**Что НЕ используем:** precision@k, nDCG, hit rate, распределение cosine, silhouette.

**Проблема:** probe — self-test (не семантика). Golden маленький (36 вопросов).

<a name="retrieval"></a>
## Retrieval — как организован

### Архитектура

**Режимы:**

| Режим | Что делает |
|---|---|
| lexical | BM25 (rank_bm25) |
| dense | Cosine similarity (e5) |
| hybrid | Adaptive: BM25 ≥ 20 → lexical; < 5 → dense; 5-20 → RRF |
| hybrid_bm25_heavy | RRF с w_bm25=3, w_dense=1 |
| hybrid_dense_heavy | RRF с w_bm25=1, w_dense=3 |

**Пороги:**
- `--min-score` (BM25) — default 5 (query), 0 (eval)
- `--min-dense` (cosine) — default 0.85
- `--rrf-k` — default 10

**Фильтры при build:**
- `is_index_garbage` — отсев 1909 чанков (XML, URL, таблицы чисел)

**Нормализация:**
- `normalize_greek_lookalikes` — греческие двойники
- `normalize_ocr_text` — для OCR

### Что уже работает

- Adaptive hybrid (v1: 0.46 → 0.69)
- RRF k=10
- min-dense 0.85 — убирает мусор
- Нормализация ARP4754A, NASA's
- Короткий чанк приоритетнее

### Что стоит внедрить

1. **Query expansion** — синонимы, стемминг, аббревиатуры
2. **Re-ranking** — cross-encoder (top-50 → top-5)
3. **ColBERT / late interaction**
4. **HyDE** — гипотетический ответ (нужна LLM)
5. **Metadata filter** — по doc_id, chapter
6. **Parent-child chunks** — small для поиска, large для контекста

<a name="узкие-места"></a>
## Пять самых узких мест

### Узкое место №1. Качество text_layer — не валидируется

**Суть:** берём `page.get_text()` и доверяем ему. Но S1000D → XML, DOCX → PDF → греческие, газеты → порядок span-ов.

**Последствия:**
- 20% чанков с проблемами
- Метрики занижены
- Dense не помогает

**Что делать:** валидация text_layer при ingestion.

### Узкое место №2. Единый чанкинг для разных типов

**Суть:** один пайплайн для текста, XML, таблиц, FMEA.

**Последствия:**
- XML разрезается на 3 чанка
- FMEA-строки разрезаны
- Формулы в текстовом индексе

**Что делать:** классификация блоков → разные стратегии.

### Узкое место №3. e5-small не различает семантику

**Суть:** 0.83-0.85 нерелевантным, 0.86-0.90 релевантным. Разница 0.05.

**Последствия:**
- min-dense 0.85 — компромисс
- Negative examples хрупкие
- PARA 0.77 — потолок

**Что делать:** e5-base (сделано, +0.08). e5-large — если нужно.

### Узкое место №4. Чанкинг не сохраняет структуру

**Суть:** теряется иерархия глава → пункт → подпункт. Нет метаданных о родителе. Нет связи между частями пункта.

**Последствия:**
- Ответ неполный
- Нет контекста
- Нельзя фильтровать

**Что делать:** иерархический чанкинг, parent-child, metadata.

### Узкое место №5. Нет честной оценки

**Суть:**
- probe — self-test
- golden — 36 вопросов
- нет precision@k
- нет A/B

**Последствия:**
- Метрики растут, качество не растёт
- Мусор в top-k не измеряется

**Что делать:**
- golden до 100+ вопросов
- precision@5 + nDCG
- автоматический eval
