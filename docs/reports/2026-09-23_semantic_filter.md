# Семантический фильтр формул (Issue 007) — отчёт

Дата: 2026-09-23. Задача: [`docs/issues/007_semantic_filter_and_formula_quality.md`](../issues/007_semantic_filter_and_formula_quality.md).

## 1. Итог

UniMERNet выдаёт синтаксически валидный LaTeX и для прозы, подписей, значений из
таблиц, поэтому `validate_latex` пропускал их со `status=ok`. Добавлен
семантический фильтр `is_real_formula_semantic`: он вызывается после
`validate_latex` и переводит такие регионы в новый статус `suspicious_semantic`
с причиной в `quality.notes`.

Проверка — офлайн-пересчёт статусов по JSON из прогонов на рабочем ПК
(`data/ir/page_tests/*_final/_1954_regions.json`, реальный LaTeX UniMERNet)
и ручная разметка всех 47 регионов по кропам:

| | до фильтра | после |
|---|---|---|
| регионов `status=ok` | 46 | 30 |
| из них мусор (проза, подписи, значения) | 9 | **0** |
| из них обрубки формул | 7 | 3 |
| настоящие формулы, потерянные фильтром | — | **0** |
| доля `ok`, где регион — формула | 65% | **90%** |
| доля `ok`, где формула и LaTeX пригоден | 48% | 73% |

Цель issue «precision ≥ 95%» по критерию «в `ok` нет мусора» достигнута
(0 из 30). По критерию «в `ok` только годные формулы» — нет: остаются 3 обрубка
и 5 настоящих формул с плохим LaTeX (см. раздел 5), по тексту их не отличить.

По тестам (`ok` / `suspicious_semantic`):

| Тест | до | после | цель из issue |
|---|---|---|---|
| T3 | 27 / 0 | 18 / 9 | ~17 / ~11 |
| T4 | 11 / 0 | 8 / 3 | ~8 / 3 |
| T5 | 1 / 0 | 0 / 1 | 0 / 1 |

Детекция регионов не менялась, поэтому T7–T10 остаются с нулём формул.

## 3. Правила

Проверяются по порядку, срабатывает первое:

| Причина | Условие | Пример из тестов |
|---|---|---|
| `tiny_crop` | bbox региона < 20×8 px при DPI рендера | — |
| `formula_number` | весь LaTeX — номер формулы `(I.7)`, `(3.12)` | — |
| `figure_caption` | регион перекрывает рисунок на ≥ 30% или стоит под ним в пределах 30 pt (x-перекрытие ≥ 30%), и в LaTeX нет знака отношения | подпись под графиком |
| `table_value` | регион на ≥ 70% внутри таблицы, и в нём нет математики, только числа или «переменная = число» | `6 = 0,06` в ячейке |
| `pure_numbers` | только цифры и `.,=×xX;:%` | `12,5 × 3` |
| `numeric_value` | все части — присваивания «переменная = число [единица]» | T6 p68 `m_к = 0,00052 \| m_к = 0,00088`; T3 p44 `(N = 200000, C = 1225 KZ)` |
| `truncated` | LaTeX кончается знаком отношения, или у `\frac` пустой/нечитаемый числитель или знаменатель | T3 p34 `M = -`, `\eta = \frac{I}{}`; T4 p48 `\frac{"}{…}` |
| `russian_words` | два русских слова подряд | — |
| `long_letter_run` | 4+ буквы подряд после удаления окружений, команд и отступов | T3 p34 `T y I I d T e`; p44 `n p u \ N`; T5 p25 `M O H J H O C T` |
| `prose_source_text` | в исходном OCR-тексте региона (`text=`) русское слово ≥ 4 букв или буквенная последовательность ≥ 5 | T3 p36 подписи кривых «хороший несущий винт» |
| `no_math_markers` | нет ни одного маркера из списка issue | `\mathrm{A}\,\mathrm{B}` |

Для `long_letter_run` и `prose_source_text` есть белый список математических
слов (`const`, `grad`, `arctg`, `sinh`…).

### Отличия от формулировок в issue

Каждое проверено на реальном LaTeX:

1. **Правило A.** Отступы `\,`, `\;`, `\!`, `~` и все `\команды` — разделители.
   Склеивается только `\ `: так UniMERNet разделяет буквы внутри слов. Если
   убрать все пробелы, как в issue, настоящая `4πρV₁ v r \, d r` (T4 p47,
   (III.2)) превращается в «vrdr» и отклоняется. Окружения `\begin{array}{l}`
   удаляются до поиска, иначе слово «array» отклоняет все многострочные формулы.
2. **Правило G.** В issue оно срабатывает только без математических маркеров,
   но `m_к = 0,00052` содержит `=` и не ловится. Теперь G срабатывает и на
   «переменная = число» внутри таблицы.
3. **Правило F** не трогает регион со знаком отношения, чтобы не потерять
   формулу сразу под рисунком. Подписи со значениями (`M = 0,75 (хороший…)`)
   ловятся правилами `numeric_value` и `prose_source_text`.
4. **`\frac{"}{…}` и `M = -`.** Issue ожидает `no_math_markers`, но маркеры в
   них есть (`\frac`, `_`, `=`, `-`). Добавлена причина `truncated`.
5. **Новые причины `numeric_value` и `prose_source_text`.** Без них мусор с
   T3 p44, p36 и T6 p68 оставался `ok`. `prose_source_text` смотрит на текст
   OCR-спанов региона: у подписей это русские слова или их «греческие двойники»
   (`πΟΤρe6ΗaΧ μΟΗΗΟΣΤΕ`), у формул — короткие токены.

## 5. Что осталось

1. **Три обрубка со статусом `ok`**: T3 p36 `M = Φ/Φ`, T3 p36
   `q = 37,5 i | 5/V`, T3 p40 `c_τ = ds_τ/ds`. Рамка региона режет дробь справа,
   а UniMERNet «дорисовывает» правдоподобный LaTeX. Пиксельный признак «чернила
   пересекают правую границу» проверен: классы он не разделяет (у настоящих
   `M_к = k/4`, `c_y = aR/r` граница тоже режет дробь). Это вопрос ширины
   региона на этапе детекции (`region_detect`: расширять bbox вправо, пока
   продолжается черта дроби), а не семантического фильтра.
2. **Формулы с негодным LaTeX со статусом `ok`**: T3 p41 `kb/πR` → `T∂_kK/πR`;
   T6 p61 `c_N = 75N/(½πR²ρ(ωR)³)` → `c_x = -\underbrace{75N}_2`; T3 p41
   `β = 1/2`; T3 p44 `c̄_y = 3c_τ/σ`; T4 p51 `dc_τ/dr`. В issue часть названа
   мусором, но на кропах это настоящие формулы. Это качество распознавания
   (UniMERNet / VLM recovery), фильтр их правильно не трогает.
3. **Смешанные регионы** (формула плюс строка текста: T3 p40 `c_xp = δ`,
   T4 p48 `β* = (v+V_y)/ωR`) уходят в `suspicious_semantic` по
   `long_letter_run`: формула настоящая, но LaTeX засорён текстом.

## 6. Issue 8 (кодировка): диагноз

Issue 8 вынесен в отдельную задачу, но причина найдена. **В JSON кодировка
правильная**: в `T1_title_final` и `T6_real_tables_final` «Напечатано» и
«Крутка» записаны в UTF-8, последовательностей `Рқ`, `в•Ё` в файлах нет. Все
`json.dump`/`write_text` в `ingestion/` и `scripts/` уже пишут с
`ensure_ascii=False, encoding="utf-8"`.

Кракозябры появляются при чтении в Windows PowerShell 5:

- `РқР°РҝРөСҮ…` — UTF-8, прочитанный как cp1251 (`Get-Content` без `-Encoding UTF8`);
- `в•ЁРӘв•ӨРҗ…` — двойная перекодировка: вывод Python через консоль cp866, затем
  чтение как cp1251. Воспроизвелось при `python … > file` в PowerShell:
  `η` превратилась в `╬╖`.

Как смотреть результаты без искажений:

```powershell
Get-Content data\ir\regions\_1954_regions.json -Encoding UTF8
$env:PYTHONIOENCODING='utf-8'; [Console]::OutputEncoding = [Text.Encoding]::UTF8
```

`UNREADABLE` в ячейках таблиц — настоящий отказ OCR, а не кодировка. Retry с
upsample 2.5× и Issue 9 (прогресс-бар с ETA) здесь не делались: в issue они
вынесены в отдельные задачи.
