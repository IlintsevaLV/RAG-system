# Гибрид, пороги и мусорные чанки

**Дата:** 2026-10-06

После полного dense-eval (`2026-10-05_dense_eval.md`) равные веса RRF с k=60 проигрывали и лексике на дословных вопросах, и dense на перефразах. Плотный поиск ставил XML, URL и числовые таблицы рядом с любым запросом. При полном попадании в кэш `build --dense` записывал в `meta.json` имя новой модели, хотя векторы оставались от старой.

Модель по умолчанию по-прежнему `intfloat/multilingual-e5-small`. e5-base не скачивалась. Формулы не индексируются. Ответ — чанк и место в документе. Генерации нет. RapidOCR mobile остаётся распознавателем по умолчанию.

Полный eval на 30937 чанках после этих правок не прогонялся: на этом компьютере `dense.npy` не совпадает с текущим `chunks.jsonl`. Цифры ниже — устройство поиска и подсчёт фильтра по уже собранным текстам.

## Режимы

`search` принимает `lexical`, `dense`, `hybrid`, `hybrid_bm25_heavy`, `hybrid_dense_heavy`. Режим по умолчанию у `query` и `probe` остаётся лексическим.

Обычный `hybrid` смотрит на балл BM25 верхнего строгого ответа:

- от 20 и выше ответ лексический, плотный список не участвует;
- ниже 5 ответ берётся из dense;
- между 5 и 20 списки сливаются через RRF.

Технический код вроде `ARP4754A` остаётся в слиянии, даже если в маленьком индексе его BM25 ниже 5. На полном корпусе такой код редкий и обычно сам набирает балл выше 5.

`hybrid_bm25_heavy` всегда сливает списки с весами 3 и 1. `hybrid_dense_heavy` — с весами 1 и 3. Эти два режима полосы 20 и 5 не переключают. Запросы с баллом 10–17, как «требования к прочности» (10.78 в прошлом прогоне), остаются в полосе RRF. Для дословного эталона по-прежнему подходят `lexical` и `hybrid_bm25_heavy`.

`rrf-k` по умолчанию 10 и в коде, и в командах `query` и `eval`. В прогоне 2026-10-05 k=10 на «требования к прочности гидросистем» поднимал ФАП-118, пункт 3, страница 10. k=60 уводил на НЛГ-27, пункт 27.251.

## Пороги

`--min-score` сравнивается с баллом BM25 до слияния. В `query` по умолчанию 5, в `eval` по умолчанию 0, чтобы лексический recall@1 0.9231 оставался сравнимым с отчётом 2026-10-05. `probe` порог не ставит.

Показанный балл гибрида — это вес RRF. При k=10 верхний ранг даёт около `1/11`. С порогом 5 это число не сравнивается: иначе любой гибридный ответ становился бы «не найдено». «Требования к прочности» с BM25 10.78 в гибриде остаётся.

`--min-dense` сравнивается с косинусом. По умолчанию 0.7 и у `query`, и у `eval`. Верхний dense-ответ ниже 0.7 даёт «не найдено». Баллы e5-small в прошлом прогоне лежат в 0.84–0.90, поэтому «рецепт пирога» с 0.848 этот порог проходит. Его убирает фильтр мусора после пересборки индекса.

## Мусор при сборке

`is_index_garbage` отбрасывает чанк, если выполняется любое из условий:

- два и больше XML-тега (`<para>`, `<lcMultipleSelect>`, `<description>` и любые другие);
- после вырезания `http://` и `https://` в тексте меньше 40 букв;
- в тексте нет букв (таблица чисел);
- больше половины непробельных символов — не буквы и не цифры (схемы из точек и тире, оглавление с точечными лидерами).

Пункт с обычной фразой и короткой ссылкой внутри остаётся. Счётчик пишется в отчёт сборки как «мусор».

На текущем `chunks.jsonl` (30937 чанков) фильтр помечает 1909. Среди них схемы KT-160G, оглавления с лидерами и кодовые шапки S1000D. В индекс они попадут только после новой сборки: уже записанный `chunks.jsonl` эта правка не переписывает.

## Кэш модели

`build --dense` при полном попадании в кэш больше не подменяет `embedding_model` в `meta.json`. Если переданное имя отличается от записанного, сборка предупреждает и оставляет старое. Недостающие чанки добираются той моделью, которая уже лежит в `meta.json`, а не смесью двух пространств.

`--force` сбрасывает кэш и считает все векторы новой моделью, после чего новое имя записывается. У `query` и `eval` флаг `--embedding-model` кодирует только запрос. Если он не совпадает с индексом, команда печатает предупреждение.

## Команды

```
python -m retrieval build --dense
python -m retrieval build --dense --embedding-model intfloat/multilingual-e5-base --force
python -m retrieval query "требования к прочности" --mode hybrid --rrf-k 10 --min-score 5 --min-dense 0.7
python -m retrieval query "..." --mode hybrid_bm25_heavy
python -m retrieval query "..." --mode hybrid_dense_heavy
python -m retrieval eval --gold data/ir/gold/retrieval_v1.json --mode hybrid --w-bm25 1 --w-dense 1 --rrf-k 10
```

Чтобы фильтр попал в поиск, на рабочем компьютере нужны обычный `build` и затем `build --dense` с той же моделью. Тексты оставшихся чанков не меняются, их векторы берутся из кэша по sha256, e5-small заново не считается. Пока `dense.npy` собран в старом порядке чанков, `--mode dense` векторы не подхватит.

В каталоге `data/models/multilingual-e5-small/` для поиска нужны `model.safetensors` и токенизатор. Форматы onnx, openvino и pytorch в этом прогоне не используются.

## Проверка

`python -X utf8 -m retrieval check` проходит. Синтетика фиксирует: сильный BM25 не смешивается с чужим вектором, `hybrid_bm25_heavy` держит пункт 27.1435, косинус 0.5 при пороге 0.7 не возвращается, порог BM25 5 не сравнивается с баллом RRF, XML, голый URL и таблица чисел отбрасываются, проза с короткой ссылкой остаётся, смена модели на cache hit не переписывает `meta.json`, `--force` пересчитывает векторы.
