Требования, необходимые для усиления/поддержания функциональной независимости должны
управляться на всех этапах разработки η могут приводить κ ограничениям при разработке
элементов.
Функциональная независимость доказана, когда общие источники ошибки между несколькими
наборами требований минимизированы на уровне строгости соразмерном σ серьезностью
классификации отказного состояния верхнего уровня. Если есть подозрение ο наличии источников
общих ошибок β требованиях, тогда функциональная независимость не может быть заявлена.
Функциональная независимость должна быть доказана на всех уровнях абстракции или
декомпозиции требований.
 5.2.3.2.1.2 Независимость разработки элемента
Независимость разработки элемента - свойство, при наличии которого элементы отличны, чтобы
минимизировать вероятность ошибки общего вида между элементами, разработанными по
отдельности.
Примеры ошибок, которые могут сдерживаться независимостью разработки элемента:
• Ошибки проектирования ПО (включая требования κ ПО, архитектуру ПО η τ.δ.),
• Ошибки разработки ПО (включая процессы разработки ПО, управления конфигурацией ПО
η τ.δ.),
• Ошибки конструирования аппаратуры (включая требования κ аппаратуре, архитектуру
аппаратуры η τ.δ.),
• Ошибки разработки аппаратуры (включая процессы разработки аппаратуры, управления
конфигурацией аппаратуры η τ.δ.),
• Ошибки инструментов разработки аппаратуры (генератор кода на языке описания
аппаратуры интегральных схем (VHDL), компоновщик, трассировщик η τ.δ.),
• Ошибки инструментов разработки ПО (компилятор, компоновщик, η τ.δ.).
Примеры средств достижения независимости разработки элемента:
• Различие физических принципов, например, использование гидравлики «против»
электрики,
• Различие операционных систем,
• Различие языков программирования/систем команд компьютеров,
• Различие микропроцессоров,
• Различие коллективов разработчиков η процессов.
